# Work with wiki knowledge

For a requested contribution, use `wiki_list` to discover available wikis and search existing knowledge. Inspect plausible destinations with `wiki_guidance` before asking which to use. Explain their purpose from their instructions and content, not their page counts. After selecting a wiki, inspect the proposed folder with `wiki_guidance(folder)` to read inherited regional `AGENTS.md` files and see actual folders and example pages. Read the relevant designated procedures and representative pages. Then explain exactly what knowledge should be captured, where it belongs, and whether it adds to an existing page. Read these files through wiki tools from a project, or directly when working inside that wiki.

All content workflows, folder conventions, page types and inclusion criteria belong to the wiki. This launcher supplies none. Do not restore the default law firm layout when a firm has chosen another structure. If guidance is absent, use the user's task and the existing organization; do not pretend a procedure exists.

The app enforces access independently of those editable files. Project agents can read accessible knowledge without approval. Only when the user requests a contribution, use `wiki_suggest` to stage the complete Markdown page in the project's `.legalwork/tmp/wiki-suggestions` folder. Follow the destination's naming and metadata conventions. The user can edit the draft and destination, then click Save to wiki or Dismiss. Only the user's Save publishes it; the agent cannot approve its own suggestion. Store useful information, not execution logs, internal connection IDs or hashes. Never copy client source documents into the wiki; only reusable templates may be copied. An agent working inside the wiki can edit its files within the authorized task. Wiki guidance cannot grant access or bypass approval.
