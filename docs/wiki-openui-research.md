# Reports, live dashboards, and inline wiki widgets

Research and revised architecture proposal, 11 October 2026. The authorized reversible OpenUI layer is now implemented after baseline commit c3df229d; native integration verification is in progress. The constraint is a bundled implementation using LegalWork's existing server and configured model providers, with no new paid service or subprovider. The latest storage recommendation supersedes the earlier proposal to make `.openui.json` files and large fenced JSON objects the primary authoring model.

## Recommendation

Build one reusable **LegalWork View** surface, available as a report tab, a saved wiki dashboard, and an inline block in a Markdown page. Start with a report tab that combines a readable narrative, findings, source links, metrics, and a table. Then connect the same components to live wiki queries and embed them in pages.

After revisiting the user's challenge about streaming and speed, my first implementation candidate is **standalone OpenUI with its polished bundled components, themed for LegalWork and extended with our source/data components**. Its progressive rendering, compact output, named-statement edits, and reactive query/action runtime directly match the requested experience. Keep **json-render as the comparison baseline and fallback**. Validate both against the same LegalWork corpus before committing the durable artifact format. This is an integration recommendation, not a measured end-to-end performance result.

Keep Markdown support and the existing editor while the storage boundary evolves. OpenUI composes interactive views; it does not supply a canonical database, document model, authorization system, or synchronization protocol.

## Storage decision: challenge YAML rather than inherit it

**Recommendation: structured records should become canonical for LegalWork's rich wiki, with Markdown as a supported authoring/import/export surface.** Use the existing bundled local SQLite/server architecture, not another service. OpenUI makes richer views practical, but the reason to change storage is the requested product: typed fields, relations, stable inline widgets, shared editing, and views reused across pages. Obsidian is inspiration, not a compatibility requirement.

The previous file-envelope proposal confused three choices: how agents express changes, how the app persists them, and how people export them. Neither a user nor an agent should have to rewrite YAML or a giant JSON document just to change a stage, add a dashboard, or insert a widget. Typed tools can work over today's files during migration; they do not require a database conversion to deliver that authoring improvement.

### What Notion and Obsidian actually document

**Notion.** Its 2021 engineering account describes UUID-addressed blocks with type, properties, ordered children, and permission parents. Changes are record operations batched into server transactions, with local caches and a durable queue. This is historical documented architecture, not a claim that every current private implementation detail is unchanged. [Notion's data model](https://www.notion.com/blog/data-model-behind-notion).

The current API distinguishes a page's typed property values from its child blocks. Data sources hold property schemas; pages are rows with content. The Views API creates named table, board, chart, and dashboard views, including linked views and dashboard widgets over existing data. A view stores configuration and source references rather than duplicate source rows. Access to a linked view does not grant access to its source. These are public API contracts, not guesses about physical database tables. [Pages](https://developers.notion.com/reference/page), [data sources](https://developers.notion.com/reference/data-source), [views](https://developers.notion.com/guides/data-apis/working-with-views).

Notion also explicitly provides Markdown create/read/update APIs as an alternative to block APIs, particularly for agents. Markdown is parsed into its content model; unsupported content has explicit representations and limits. This is direct evidence that a structured canonical model can still offer convenient Markdown authoring. [Markdown API](https://developers.notion.com/guides/data-apis/working-with-markdown-content).

Its 2025 offline engineering article describes persistent SQLite storage that tracks a page's complete dependencies, refresh subscriptions, and migration of offline pages to a CRDT model. A database alone does not make offline editing or conflict resolution correct. Markdown/CSV exports also do not instantly reconstruct a full Notion workspace, which is a portability weakness we should avoid. [Offline engineering](https://www.notion.com/blog/how-we-made-notion-available-offline), [export limitations](https://www.notion.com/help/back-up-your-data).

**Obsidian.** Markdown files are canonical; metadata caches are rebuildable. Properties are YAML frontmatter with a friendly field UI and types shared by property name across the vault. Bases stores view definitions, filters, and formulas in YAML `.base` files, normally edited through the UI, and queries the notes rather than copying their rows. Thus YAML can support polished views without becoming the user interface. Its shared-vault documentation explicitly excludes live collaboration on the same file and fine-grained access. [Storage](https://obsidian.md/help/data-storage), [properties](https://obsidian.md/help/properties), [Bases syntax](https://obsidian.md/help/bases/syntax), [collaboration](https://obsidian.md/help/sync/collaborate).

### Three viable storage choices

| Choice | Strength | Cost for our requested product |
| --- | --- | --- |
| Markdown + YAML canonical | Existing behavior, simple backups, arbitrary external editors, portable prose, rebuildable index. Good fit if folder interoperability is the primary product promise. | Typed field renames and relations need an additional schema layer; page/block identity must survive file changes; record edits conflict at file level; cross-page/view updates are not a transaction. OpenUI does not remove these limits. |
| Canonical structured records + Markdown APIs/import/export | Stable page/block/field/view IDs; transactional field edits; direct indexed queries; references survive renames; inline widgets are real blocks; changes can sync at record level. Best fit for a shared Notion-like wiki. | Requires migration, backup/restore, conflict and offline design, and an explicit external-file bridge. Plain Markdown cannot losslessly represent every advanced block or view. |
| Markdown prose + canonical metadata/view database | Preserves ordinary prose files while improving fields, schemas, relations, and view reuse. Useful as a deliberate transition. | Two storage systems must commit/recover together. A folder copy is incomplete without its metadata. Durable widget positions and external file edits still need identifiers and reconciliation. Maintaining two writable copies of the same properties is particularly error-prone. |

**Choose the structured model as the destination.** A hybrid is sensible only with explicit ownership: one authoritative location for each fact, an operation journal, and recoverable file projection. It is not a shortcut around synchronization engineering. If unrestricted external-folder editing later becomes the overriding requirement, choose the Obsidian model consciously and accept its collaboration limits; do not claim both models' guarantees at once.

### What this changes in our proposal

- Give pages, blocks, field definitions, relation targets, and views stable IDs. Names and paths are presentation/export metadata. A rename must not break a view or relation.
- Keep page content separate from typed values. Markdown remains a compact input/output for prose. Unsupported imported syntax must remain an opaque, losslessly retained content block, not disappear on save.
- Store an OpenUI program, catalog version, typed query bindings, and revision in a **view record**. Inline content contains a **view-reference block** with a durable block ID. Full-page tabs open the same view ID. A copied placement can reference the same view or explicitly duplicate it.
- Keep live query results out of the saved view definition. A frozen report instead owns an immutable data/provenance snapshot with source revisions and an as-of time. Refresh creates a new report revision.
- Add typed user/agent operations such as `wiki_page_create`, `wiki_properties_update`, `wiki_query`, `wiki_view_create/update`, and `wiki_block_insert/move`. Give agents a discoverable component catalog and field schema. Prose tools may accept Markdown. The server validates, assigns IDs, records revisions, and persists the result.
- OpenUI's compact language is appropriate for the generated layout itself. Bindings and changes should be structured tool arguments, not escaped YAML or a serialized file envelope the model must reconstruct. `.openui.json` can remain an interchange/export format; it is not the primary object model.
- Sync records/operations through the existing LegalWork service with idempotency, revisions, tombstones, and a durable local outbox. Do not sync a live SQLite file as an attachment. A CRDT may be appropriate for simultaneous rich-text editing, but is a separate implementation choice, not an automatic benefit of SQLite.
- Support external Markdown as import/open/edit/export first. If bidirectional folder projection is offered, retain export baselines and IDs, merge only independently changed portions, and surface ambiguity. Repeated paragraphs, split/merged blocks, or a lost sidecar cannot be safely resolved by title matching.

### Migration grounded in the current code

Today `wiki/store.ts` keys cached pages by `(wiki,path)`, reparses Markdown/frontmatter, and hashes the whole file as its revision. `wiki/markdown.ts` extracts dynamic properties and `Views.md` configuration. `wiki/sync.ts` synchronizes per-file SHA revisions, merges text when possible, and retains conflicting copies. The editor's current Lexical keys are not durable cross-session block IDs. These are useful existing capabilities, but they are not a canonical typed record store.

1. Preserve and finish the baseline. Introduce a repository/service boundary and typed field/view/block operations, initially adaptable to the file model. Stop teaching agents to edit `Views.md` or hand-author serialization to perform ordinary UI actions.
2. Add canonical record tables and migration tooling behind that boundary. Import each wiki into a new store while retaining original files and a migration manifest with original hashes, IDs, unknown YAML, and unsupported Markdown. Validate page count, typed values, links, assets, and readable exports before switching that wiki's authority.
3. Preserve existing Markdown opening and editing. For migrated pages, translate Markdown changes into content operations with revision checks and durable-ID reconciliation. Keep genuinely unsupported syntax opaque. Do not normalize away material the new model cannot represent.
4. Add record synchronization and offline outbox recovery before migrating shared wikis. Keep old clients from dual-writing the same wiki through legacy file sync. Test concurrent independent fields, same-field conflicts, block moves/deletes, access revocation, and reconnect.
5. Prove a lossless LegalWork backup/restore bundle separately from readable Markdown/CSV export. The full bundle includes schema, IDs, relations, views, source snapshots, and assets. Portability is an acceptance test, not an assertion that Markdown alone preserves everything.

This is a larger architectural change than adding a renderer. It should be its own migration after the baseline, not slipped into the renderer commit. A first OpenUI report prototype can use an in-memory/repository-backed view object now without making the old file-envelope idea a permanent contract.

## What OpenUI actually provides

The requested product is Thesys's OpenUI. Its component catalog, parser, prompt generator, and React renderer can be installed locally. The core and React packages are MIT licensed, so bundling is supported subject to preserving the license notices. The published `@openuidev/react-lang` and `@openuidev/lang-core` versions checked today are **0.4.1**, released 10 October. Pin and test a specific version rather than following `latest`. [License](https://github.com/thesysdev/openui/blob/main/LICENSE), [React package](https://github.com/thesysdev/openui/blob/main/packages/react-lang/package.json), [published metadata](https://registry.npmjs.org/@openuidev/react-lang/latest).

OpenUI Lang is a line-oriented component description. We register typed components, generate a catalog prompt, obtain text from the existing agent/model, and render it progressively. The model does not provide arbitrary React code. The renderer and generation transport are separable, so adopting OpenUI does not require replacing LegalWork's chat or agent system. [OpenUI Lang](https://www.openui.com/docs/openui-lang), [integration guide](https://www.openui.com/docs/getting-started).

Its `$variables` support input bindings. `Query` calls an application-supplied tool and re-fetches when referenced state changes; `Mutation` executes an explicitly triggered write. A plain function map is supported, so we can connect only our wiki query API. Filtering a generated dashboard need not call an LLM. Periodic query refresh is also available. External wiki edits still need our invalidation/subscription adapter; reactive input binding alone does not provide that. [Architecture](https://www.openui.com/docs/openui-lang/architecture), [reactive state](https://www.openui.com/docs/openui-lang/reactive-state), [queries and mutations](https://www.openui.com/docs/openui-lang/queries-mutations).

The current quickstart is unsuitable verbatim: both displayed provider examples use a `THESYS_API_KEY`, with Gateway or Autofix in the path. Autofix sends the conversation and generated interface to a Thesys endpoint and charges for attempted repairs. Exclude Gateway, Autofix, cloud monitoring, hosted previews, and the scaffolder's service setup. Use local validation and, if necessary, a bounded repair through the already configured provider. [Getting started](https://www.openui.com/docs/getting-started), [Autofix](https://www.openui.com/docs/autofix).

Installation telemetry is enabled by default; runtime telemetry is opt-in. If OpenUI is chosen, set `OPENUI_TELEMETRY_DISABLED=1` for installation, CI, and the bundled server, and do not enable its cloud observability sink. Verify the packaged app with network interception. This is required by the user's constraint, even if telemetry contains only installation metadata. [Telemetry documentation](https://www.openui.com/docs/openui-lang/telemetry).

## Reassessment: why OpenUI's streaming and speed matter

The earlier json-render-first recommendation over-weighted JSON familiarity and existing cache integration. It under-weighted the user-visible result: a useful interface appearing while the agent is still answering, economical follow-up edits, and widgets that continue working without another model call. I also failed to inspect OpenUI's published reliability benchmark and the actual streaming implementations before ranking the options. Those omissions change the recommendation. Hosted quickstart examples do not diminish the standalone runtime's capabilities.

| Concern | Strongest case for OpenUI | Like-for-like json-render comparison |
| --- | --- | --- |
| Streaming granularity | Its parser can materialize the incomplete trailing component, including partial text, while completed statements remain cached. Forward references fill in later. | The standard SpecStream compiler applies complete JSONL patch lines. It also streams, but a long text value in one unfinished patch is not yet applied. Smaller patches can improve this at additional wire overhead. |
| First useful interface | A short root and heading can become useful early, then tables/charts fill in. In React 0.4.1, new query evaluation waits until streaming finishes, so earlier visible content does not imply earlier live data. | It can also emit root/parents first and populate children progressively. Root ordering, component loading states, chunking, and when data arrives matter in both. |
| Generation speed and tokens | Positional component calls avoid repeating property names and patch envelopes. This is a meaningful advantage when output generation is the bottleneck. | JSONL carries more structural syntax. Compact catalogs, short IDs, and chunking strategy narrow the gap; the actual data and prose still need transmission in either format. |
| Local edits | A follow-up can replace a few named statements and keep the rest. That suits “add a chart” or “group by partner.” | JSON Patch already supports partial updates. OpenUI's advantage is compactness and statement-oriented authoring, not exclusive ownership of incremental editing. |
| Recovery | Known good components can remain visible, while structured errors identify malformed components or references for a repair through our existing provider. | A malformed JSONL line need not destroy the whole interface. The standard compiler skips invalid lines; we must detect missing structure instead of accepting silent partial success. |
| Live data and actions | `$variables`, `Query`, `Mutation`, `@Run`, `@Set`, and `@Reset` make a generated widget behave like an app without repeated LLM calls. | State bindings, watchers, registered actions, and external stores cover similar building blocks. We would supply more query orchestration ourselves. |
| Parsing CPU | Completed statements are cached. Partial rendering does additional validation and materialization work each update. | Patch application avoids parsing the previous whole document. Neither implementation establishes a general parser-speed winner without equivalent validation and rendering work. |

Implementation and API sources: [OpenUI streaming parser](https://github.com/thesysdev/openui/blob/main/packages/lang-core/src/parser/parser.ts), [renderer](https://www.openui.com/docs/openui-lang/renderer), [incremental editing](https://www.openui.com/docs/openui-lang/incremental-editing), [actions](https://www.openui.com/docs/openui-lang/interactivity), [json-render streaming](https://json-render.dev/docs/streaming), [state bindings](https://json-render.dev/docs/data-binding), [json-render core source](https://github.com/vercel-labs/json-render/tree/main/packages/core/src).

The query qualification comes from inspecting the published React package: `useOpenUIState` blocks new query evaluation and mutation registration while `isStreaming` is true. Existing cached results and the existing bare-language query lifecycle can remain available during an edit. If we need fresh data to appear before the initial generation completes, LegalWork must prefetch the authorized dataset itself or expose separately completed widgets. Do not claim the library does this automatically. [Runtime implementation](https://github.com/thesysdev/openui/blob/main/packages/react-lang/src/hooks/useOpenUIState.ts).

### What the benchmarks establish

OpenUI's seven-example serialization benchmark reports **4,800 output tokens versus 10,180** for json-render, a **52.8% reduction** in that corpus. The dashboard is **1,226 versus 2,247**. Its advertised latency is calculated at a fixed 60 tokens/second, not measured time to a painted interface. Samples are generated as OpenUI and converted to other formats, so this establishes a compact representation, not independently measured generation quality or speed. It is still meaningful evidence for lower output cost and a shorter generation tail. [Token benchmark and methodology](https://www.openui.com/docs/openui-lang/benchmarks).

The converter visits child nodes before parents and writes JSON patches in that insertion order. Consequently its root element definition arrives last. That is an unfavorable order for json-render's first useful render and should not be copied into our comparison. Emit root and visible structure early for both libraries, and compare equivalent component/data representations. This does not invalidate the reported token counts; it prevents using these samples to prove an early-render advantage. [Spec converter](https://github.com/thesysdev/openui/blob/main/benchmarks/vercel-spec-converter.ts), [JSONL converter](https://github.com/thesysdev/openui/blob/main/benchmarks/vercel-jsonl-converter.ts).

There is also a more substantial vendor study: 46 briefs, 70 equivalent components, four runs per brief, six models, and committed raw outputs. It reports lower output usage and stronger structural validity for OpenUI than json-render. I should have included that evidence initially. However, its catalog originates in OpenUI's components, it scores structural completeness rather than visual/task correctness, and its pinned versions are OpenUI core 0.2.16 and json-render 0.19, not today's 0.4.1/0.21.0. Its token ceiling also gives a compact format more room to finish, a real operating advantage but not a format-independent quality test. [Benchmark repository](https://github.com/thesysdev/generative-ui-bench), [methodology](https://www.openui.com/benchmarks/methodology).

The blog's headline, tables, and narrative currently disagree on some aggregate percentages and blank-screen counts. I would use the pinned raw results for a reproducible comparison rather than repeat one selected headline. The study is directional evidence in OpenUI's favor, not an independent production guarantee. Hosted Gateway repair percentages are excluded from the standalone comparison. [Vendor reliability article](https://www.openui.com/blog/generative-ui-benchmark).

### Small local runtime check

I installed only the two parser packages and Zod in a temporary directory, with scripts and OpenUI telemetry disabled. No app dependency or provider was added. On Node 24.11.0, OpenUI core 0.4.1 produced a partial `TextContent` node from `root = TextContent("Reviewing Acme` before the closing quote/parenthesis arrived. json-render core 0.21.0 produced no patch from the equivalent unfinished JSONL line, then applied it on completion. OpenUI preserved valid siblings around an unknown component and returned a structured error. json-render preserved state across a malformed JSONL line and accepted the next valid patch.

This verifies the different streaming/error semantics. It does not measure model generation, browser paint time, frame rate, or overall renderer performance. It also disproves the overly broad comparison that “broken JSON means a blank screen” when the actual alternative is streaming JSONL.

### Decision criteria

Prototype OpenUI first. For the same report, stage dashboard, and inline widget, measure time to first meaningful content, first usable data interaction, final usable interface, input/output/retry tokens, semantic correctness, and p50/p95 results. Keep provider/model/settings, component semantics, root-first ordering, dataset delivery, and network conditions equal. Test partial text, delayed queries, truncated output, a bad statement, a broken reference, and a follow-up edit. Separately profile parser CPU, React commits, and bundle size; do not present lower token counts as proof of a faster parser.

Choose OpenUI if that prototype delivers the earlier useful interface and smaller output its design suggests while preserving task correctness, local operation, and bounded resource use. Use json-render if it wins those measurements or OpenUI's runtime behavior proves unsuitable. JSON storage familiarity alone is not a reason to give up the stronger OpenUI experience. A versioned artifact envelope can store validated OpenUI Lang plus source bindings and state, so persistence does not force a JSON UI language.

## The feature to build

**Report tab.** An agent in any authorized project or wiki can create an interactive report artifact. It opens in the normal workspace tab system with persisted tab identity and source links that open actual files/pages. The first catalog should cover sections, Markdown text, findings, metrics, tables, simple charts, and source references. A report is frozen by default: it records source revisions and an as-of time, so an already reviewed conclusion does not silently change when a wiki field changes. A deliberate refresh creates a new revision.

**Live wiki dashboard.** A saved page such as “Clients” shows clients grouped by engagement stage, a sortable table, and counts using typed indexed fields. A due-dates widget can filter by responsible lawyer and date. These are computed from source records, not numbers invented or repeatedly recalculated by the model. User filters update locally or query the server. Source edits invalidate relevant queries. Every result row opens its original wiki page.

**Inline widget.** The same view can appear between paragraphs: a related-matters table, client stage board, deadline list, or a small metric/chart. Give it a compact hover/focus menu for settings, source, and “Open in tab.” Ordinary reading should not look like a dashboard builder. Inline and full-tab versions share identity and data bindings; changing a filter does not rewrite the Markdown unless the user saves that as the default.

## Integration with the code we have

- `panel-tab-store.ts` and `side-panel.tsx` already own tab persistence and pane destinations. A report should use that system rather than an overlay or a second navigation model.
- `WikiMarkdownEditor` wraps the shared MDXEditor implementation. Register a custom code-block editor for a dedicated fence. Preserve its source exactly through rich/source editing and fallback to a readable placeholder if a runtime/version is unavailable.
- `WikiViewPane` already renders tables and stage boards from `WikiPage.properties`. Reuse those components and page navigation, while moving dataset selection, aggregation, and pagination to a bounded server query surface.
- `WikiStore` already has a SQLite-derived index and revision-aware Markdown files. At inspection, the public surface exposes snapshots/search rather than the structured dashboard query API we need. Building data views must not repeatedly load all page bodies or parse every file in the renderer.
- `reviews/report-data.ts` already produces report packets with source hashes, revisions, counts, and evidence references. Add a dataset adapter for those packets so review agents benefit from the report viewer as well as wiki agents.
- `html-preview-security.ts` and `preview.tsx` already isolate HTML artifacts with `sandbox="allow-scripts"`, a restrictive CSP, and a narrow PDF bridge. Preserve that route for custom HTML. Do not grant generated HTML general wiki/server access to implement dashboards.

These are local code findings from this checkout, not upstream library features. The editor, graph, and original-file fixes being implemented in parallel may change these integration points.

## Reversible implementation boundary

The first OpenUI layer will **not migrate existing wiki pages**. A view repository exposes stable IDs, revisions and typed operations, initially persisting each view through the existing revision-checked file/sync service. This is a storage adapter, not a requirement for humans or agents to author JSON. It retains file-level conflict semantics and can later be replaced by the structured store recommended above.

Each managed view record is validated on read as well as write, includes its ID, and atomically contains its frozen data when it is a report. Duplicate IDs and sync conflict copies must be visible; they cannot be resolved by arbitrary filesystem order. Renaming the displayed title must retain identity. Internal storage paths stay behind the repository. An inline `legalwork-view` fence contains only a view reference; the program, bindings and datasets are not copied into page prose. A workspace-owned counterpart is needed so an ordinary project agent can create a private report without publishing into a wiki.

Frontend integration can reuse `panel-tab-store.ts` for persisted view tabs and pane destinations. MDXEditor exposes `appendCodeBlockEditorDescriptor$`, so a focused plugin can render the reference in place while retaining ordinary Markdown source. Its React context will provide the active server and wiki/workspace owner; no server URL or credential belongs in the Markdown fence. Read-only Markdown must use the same reference renderer. Broken, inaccessible, and unsupported-version views must leave the surrounding prose editable.

For streaming, OpenCode's current SDK has a `raw` argument string on pending tool parts. Our `parseDynamicToolUIPart` drops pending tools whose parsed input is empty, and does not retain that raw string. A narrow bridge for the view tools can retain it and feed the existing AI SDK's partial JSON parser, then OpenUI's partial program renderer. Actual progressive delivery needs validation against the running engine/provider; an `input-streaming` label on a running tool is not evidence of streamed arguments. Until complete validation, previews must not execute data queries or actions or overwrite the saved revision.

The preferred stock-component dependency arrangement is an isolated workspace adapter with its own compatible Zustand 4 peer graph, leaving the app on Zustand 5. Published component subpaths and the GenUI entry do not directly import `react-headless`; the root UI entry re-exports chat/headless. Use the narrow entry points and verify the production graph. If headless is installed solely to satisfy the published peer metadata, that does not require shipping or invoking its runtime.

## Proposed OpenUI integration after the storage decision

The runtime contract is independent of persistence: a view revision supplies title, mode, catalog version, OpenUI program, named typed query bindings, optional frozen datasets, and readable fallback content. The storage service supplies identity and revision; neither lives inside arbitrary agent-authored executable code. Export may serialize that object, while normal editing goes through operations.

For live data, a program can use `Query("wiki_query", {name: "clients"}, {rows: [], total: 0})`. A narrow function map resolves only bindings registered to that view and calls the authorized query API. Unknown aliases reject. Queries select known field IDs with bounded filter/sort/group/aggregate operations, pagination and source revisions. No generated SQL, unrestricted MCP client, arbitrary fetch, or shell capability is exposed. Report mode resolves the same aliases from its frozen datasets. Local filter state must show when it only covers a truncated page of results.

OpenUI owns interaction dependencies. LegalWork owns authorization, shared query caching, source invalidation, and the record operation layer. New queries currently wait for generation to finish; early visible narrative and component shells still stream. To show fresh data earlier, prefetch known authorized bindings independently. Separate first visible content from first usable interaction in measurement. A tool that only receives complete arguments cannot by itself demonstrate streaming: wire partial program events from the existing agent stream into an ephemeral preview, then validate and save the complete view revision. Do not call a finished-file reload a streaming implementation.

Register the library/catalog once and discover current fields through tool results, respecting stable session prompts. Agents should be able to create a report from any authorized workspace through the bundled tools. They should not need a wiki-only chat, a new provider, a hosted renderer, or a second conversation stack.

## Actual OpenUI component library and theme

## Implemented reversible layer

The bundled adapter uses `@openuidev/react-lang` 0.4.1 and stock `@openuidev/react-ui` 0.17.1 components through narrow subpath imports. Its Zustand 4 peer graph is isolated in `packages/openui`, leaving the app on Zustand 5. Cards, metrics, tables, charts, tags and callouts use the stock library, with LegalWork typography and color tokens. A read-only board groups indexed fields and opens the source page for editing.

Views have dedicated persisted workspace tabs. Saved `.view.json` dashboard and report files appear in wiki and project file trees with their titles and file types. Project tabs also expose Reports under the plus menu. Markdown `legalwork-view` fences retain only a durable reference and render through the same authenticated view host in editable and read-only pages. A missing or broken view leaves surrounding prose intact. Typed agent tools supply the catalog and record operations. Source ownership travels with frozen datasets so a project report can open a cited wiki page without misrouting it into the project.

The pending OpenCode raw-argument bridge and AI SDK partial JSON parser feed incremental program text into OpenUI with interactions and query execution disabled during generation. The parser and bridge are covered by focused tests, including an unfinished string becoming visible. This establishes the UI path; provider-level event cadence still requires a real streamed generation check before promising an end-to-end latency improvement. Live views poll the authorized data adapter, display truncation, and reports use their frozen datasets. Filtering/sorting in the displayed table is local to those rows.

A package review found that React Lang 0.4.1 auto-mounts an optional development inspector whose wrapper imports executable JavaScript from jsDelivr. Both app Vite configurations alias that optional inspector to a local no-op. Renderer observability is disabled. Generated cloud bundles, Script and Mutation programs are rejected, and the tool map exposes only named saved data queries. No new model provider, hosted renderer, runtime CDN, or telemetry integration is introduced.
